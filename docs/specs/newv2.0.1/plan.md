# RAG Task newv2.0.1 Plan

작성일: 2026-04-13  
상태: Active

## 완료 표시 규칙

- `[ ]` 미완료
- `[-]` 진행 중
- `[x]` 완료

## 실행 원칙

1. 목표는 문서 QA 개선이 아니라 OCP API 기반 운영 챗봇 전환이다.
2. 속도를 최우선으로 한다.
3. 상태 질의는 OCP API만으로 끝내는 경로를 기본값으로 둔다.
4. 문서 RAG는 기본 경로에서 제외한다.
5. 문서 RAG는 설명 요청일 때만 선택적으로 사용한다.
6. 현재 요구사항과 맞지 않는 레거시 RAG 경로는 유지하지 않는다.
7. 모든 문서와 코드는 UTF-8을 유지한다.

## 제품 방향 요약

- `pods`, `deployments`, `services`, `routes`, `events` 기반 read-only 운영 챗봇
- 멀티턴 질의응답으로 drill-down 가능한 구조
- 문서 RAG는 보조 기능
- Lightspeed 대체가 목표
- 응답 속도 최적화가 최우선 과제

## 현재 판단

현재 병목은 문서 RAG 전체보다 다음 요소에 집중되어 있다.

- broad retrieval
- 불필요한 reranker 호출
- preview/source card 중심 UI 경로
- 상태 질의에도 개입하는 문서 보조 흐름

따라서 `문서 RAG를 완전 삭제`하기 전에, 먼저 `기본 경로에서 제거`하고 `설명 요청 전용 보조 경로`로 축소하는 것이 우선이다.

## Phase Plan

### Phase 1. 기본 경로 전환

목표:
- 상태 질의 기본 경로를 OCP API 전용으로 전환

작업:
- [ ] 상태 질의와 문서 설명 질의를 명확히 분기
- [ ] 기본 질의에서 문서 retrieval 호출 제거
- [ ] 문서 설명 요청만 보조 경로로 연결

완료 기준:
- Pod/Deployment/Service/Route/Event 관련 질문은 문서 RAG 없이 응답한다.

### Phase 2. 멀티턴 리소스 문맥

목표:
- 리소스 기반 멀티턴 대화 완성

작업:
- [ ] 최근 조회한 리소스 타입 저장
- [ ] 최근 조회한 리소스 이름 저장
- [ ] 최근 결과 집합 저장
- [ ] `그중`, `그 YAML`, `그 Pod` 같은 후속 질의 해석 강화

완료 기준:
- 리소스 drill-down이 직전 응답 맥락을 따라간다.

### Phase 3. 상태 응답 포맷 정리

목표:
- 운영용 답변 형식 표준화

작업:
- [ ] 개수/목록/상태 요약 템플릿 정리
- [ ] namespace 반영 방식 정리
- [ ] YAML 응답 길이 정책 정리
- [ ] Event 요약 형식 정리

완료 기준:
- 상태 질의 응답 형식이 일관되고 짧고 명확하다.

### Phase 4. 속도 최적화

목표:
- 현재 문서 RAG로 인한 지연을 제품 기본 경로에서 제거

작업:
- [ ] 상태 질의에서 reranker 제거
- [ ] 상태 질의에서 preview/citation 부하 제거
- [ ] retrieval candidate 축소
- [ ] 느린 초기화 경로 로그 기준 병목 제거

완료 기준:
- 상태 질의는 빠르게 응답하고 문서 단계 병목을 거의 타지 않는다.

### Phase 5. 문서 보조 경량화

목표:
- 문서 보조를 작고 예측 가능한 기능으로 축소

작업:
- [ ] `openshift-docs` 핵심 subset만 유지
- [ ] customer guide는 명시 요청일 때만 사용
- [ ] 공식 PDF 의존도 축소
- [ ] low-signal chunk 제거 유지

완료 기준:
- 문서 설명 요청만 문서 경로를 사용한다.

### Phase 6. 레거시 제거

목표:
- 새 방향과 맞지 않는 코드/문서/UX 제거

작업:
- [ ] 버전 질문 제거
- [ ] broad source card 제거
- [ ] preview 남용 경로 제거
- [ ] obsolete RAG-heavy 코드 인벤토리 작성 후 제거

완료 기준:
- 기본 UX가 운영 챗봇 중심으로 정리된다.

## 즉시 우선 작업

1. 상태 질의에서 문서 retrieval을 기본적으로 끊는다.
2. customer guide가 새 채팅 기본 응답원이 되지 않게 한다.
3. OCP API 응답 형식을 운영자 친화적으로 정리한다.
4. 문서 설명 요청만 별도 보조 모드로 태운다.

## 제거 후보

- broad 문서 retrieval
- 상태 질의에도 개입하는 heavy reranker
- source card / preview card 과다 노출
- 버전 clarification
- chunk viewer 중심 문서 UX
- 공식 PDF 중심 흐름

## 검증 기준

### 기능 검증

- `현재 Pod 몇 개야?`
- `pandas 이름으로 된 요소 알려줘`
- `그중 Pod만 보여줘`
- `그 YAML 값이 뭐야`
- `Warning 이벤트만 요약해줘`

위 흐름이 문서 RAG 없이 자연스럽게 이어져야 한다.

### 성능 검증

- 상태 질의는 문서 질의보다 현저히 빨라야 한다.
- 느린 병목이 retrieval/reranker/preview에서 발생하지 않아야 한다.
- 첫 응답 체감 지연이 줄어야 한다.

### UX 검증

- 깨진 텍스트가 없어야 한다.
- 버전 질문이 없어야 한다.
- 불필요한 source card가 없어야 한다.
- 상태 질의는 곧바로 결과를 보여야 한다.
