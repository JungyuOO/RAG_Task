# RAG Task newv2.0.1 Spec

작성일: 2026-04-13  
상태: Draft

## 1. 목적

`newv2.0.1`의 목적은 기존 문서 중심 RAG 챗봇을, 실제 OpenShift 클러스터 상태를 우선적으로 조회하고 설명하는 운영형 멀티턴 챗봇으로 전환하는 것이다.

이 버전에서 제품의 중심은 문서가 아니라 OCP API다.

- 사용자는 현재 클러스터의 `pods`, `deployments`, `services`, `routes`, `events` 상태를 묻는다.
- 챗봇은 OCP API에서 읽어온 실제 상태를 기준으로 답한다.
- 문서 RAG는 기본 경로가 아니라 보조 경로다.
- 목표는 “문서를 요약하는 챗봇”이 아니라 “OpenShift Lightspeed를 대체할 수 있는 read-only 운영 챗봇”이다.

## 2. 핵심 방향

### 2.1 기본 응답 경로

기본 응답 경로는 OCP API여야 한다.

- 상태 질의: OCP API 직행
- 리소스 drill-down: OCP API 직행
- YAML 조회: OCP API 직행
- 문서 설명 요청: 보조 경로로 문서 사용

즉, 문서 RAG는 기본 경로에서 제외한다.

### 2.2 제품 우선순위

우선순위는 다음과 같다.

1. OCP API 기반 상태 질의 정확도
2. 멀티턴 리소스 문맥 유지
3. 응답 속도
4. YAML drill-down
5. 운영자 친화적 응답 형식
6. 문서 설명 보조

### 2.3 성능 우선 원칙

속도는 최우선 목표다.

- 상태 질의에 문서 retrieval을 기본 적용하지 않는다.
- 상태 질의에 cross-encoder reranker를 적용하지 않는다.
- 상태 질의는 가능한 한 `intent -> OCP API query -> response formatting`만으로 끝낸다.
- 문서 RAG는 명시적 설명 요청일 때만 제한적으로 수행한다.

## 3. 주요 사용자 시나리오

### 3.1 상태 요약 질의

사용자는 다음과 같은 질문을 한다.

- 현재 배포되어 있는 Pod 갯수가 몇 개야?
- 지금 돌아가고 있는 건 뭐야?
- pandas 이름으로 되어있는 요소가 알려줘.
- 현재 Warning 이벤트만 보여줘.

챗봇은 리소스 유형별로 현재 상태를 요약해야 한다.

예시 응답 형태:

- `pandas 관련 리소스는 Pod 3개, Deployment 1개, Service 1개가 있습니다.`
- `Pod: ...`
- `Deployment: ...`
- `Service: ...`

### 3.2 멀티턴 drill-down

사용자는 직전 결과를 이어서 묻는다.

- 그중 Pod만 다시 보여줘.
- 그 Pod YAML 값이 뭐야?
- 그 Service는 어떤 Route와 연결돼 있어?
- 해당 Deployment 상태가 정상인지 보여줘.

챗봇은 직전 응답에서 선택된 리소스 집합과 리소스 타입을 기억해야 한다.

### 3.3 문서 설명 보조

다음 질문은 문서 보조가 필요한 경우다.

- Pod 구성 방식 설명해줘.
- Service와 Route 차이 설명해줘.
- MTU 변경할 때 주의사항 알려줘.

이 경우에도 문서는 주 응답원이 아니라 설명 보조 자료 역할이다.

## 4. 기능 요구사항

### 4.1 지원 리소스

최소 지원 리소스:

- Pods
- Deployments
- Services
- Routes
- Events

### 4.2 지원 질의 유형

최소 지원 질의:

- 전체 개수
- 이름 목록
- 이름 패턴 검색
- namespace 범위 제한
- 상태/phase 요약
- 특정 리소스 YAML 조회
- 이벤트 요약

### 4.3 멀티턴 상태 저장

세션 상태에 최소 다음을 저장해야 한다.

- 현재 namespace
- 최근 조회한 리소스 타입
- 최근 조회한 리소스 이름
- 최근 필터 키워드
- 최근 결과 집합

### 4.4 응답 형식

상태 기반 응답은 다음 형식을 따른다.

1. 직접 답변
2. 리소스 유형별 요약
3. 필요 시 항목 목록
4. 필요 시 다음 drill-down을 유도하는 짧은 안내

불필요한 문서 source card, preview card, 과도한 citation UI는 기본으로 노출하지 않는다.

### 4.5 YAML 응답

특정 리소스 YAML을 요청하면 다음 중 하나를 수행한다.

- YAML 전문 제공
- 길면 핵심 필드 요약 + YAML 보기 경로 제공

이 응답은 문서가 아니라 OCP API 결과 기준이어야 한다.

## 5. 문서 RAG 역할 재정의

문서 RAG는 유지하되 역할을 축소한다.

### 5.1 문서 RAG 사용 조건

문서 RAG는 다음 조건에서만 사용한다.

- 사용자가 개념 설명을 요청한 경우
- 사용자가 절차/가이드 설명을 요청한 경우
- 사용자가 명시적으로 문서 기준 설명을 원한 경우

### 5.2 문서 RAG 비사용 조건

다음 경우에는 문서 RAG를 기본적으로 사용하지 않는다.

- 현재 상태 확인
- 리소스 목록 조회
- 리소스 필터링
- YAML 조회
- 이벤트 상태 확인
- 리소스 간 관계 조회

### 5.3 문서 우선순위

문서가 필요한 경우 우선순위는 다음과 같다.

1. `openshift-docs`에서 가져온 핵심 Markdown
2. 고객사 가이드
3. 필요한 경우만 공식 PDF

## 6. 비목표

이 버전의 비목표는 다음과 같다.

- 광범위한 공식 문서 검색 서비스
- PDF 중심 자료실 UX
- 문서 chunk viewer 중심 설계
- 버전 선택/버전 clarification 흐름
- 고객사 가이드를 기본 우선순위로 사용하는 retrieval
- OCP write 작업 자동화

## 7. 제거 또는 축소 대상

다음 요소는 기본 경로에서 제거 또는 축소 대상이다.

- broad 문서 retrieval
- 상태 질의에도 개입하는 문서 rerank 경로
- source card / preview card 과다 노출
- 문서 중심 citation UX
- 버전 질문
- PDF 중심 공식 문서 UX

## 8. 아키텍처 원칙

### 8.1 OCP API 우선

질의 처리의 1차 분기는 “OCP API로 답할 수 있는가”여야 한다.

- 답할 수 있다면 OCP API 경로로 종료
- 답할 수 없다면 보조 문서 경로 사용

### 8.2 retrieval 최소화

retrieval은 기본 엔진이 아니라 선택 기능이어야 한다.

- 상태 질의 기본 경로에서는 retrieval을 호출하지 않는다.
- 문서 설명 요청에서만 retrieval을 호출한다.
- 문서 retrieval도 candidate 수를 강하게 제한한다.

### 8.3 source_path 정규화

Windows 경로, Docker 경로, 상대 경로 차이로 동일 문서가 중복 적재되지 않도록 정규화한다.

## 9. 성공 기준

### 9.1 기능 성공 기준

- Pod/Deployment/Service/Route/Event 상태 질의가 자연어로 가능하다.
- 멀티턴 drill-down이 자연스럽게 이어진다.
- YAML 조회가 가능하다.
- 문서 설명 질문은 필요할 때만 문서 보조로 연결된다.

### 9.2 성능 성공 기준

- 상태 질의 응답 속도는 현재보다 현저히 빨라야 한다.
- 느린 병목이 문서 retrieval, reranker, preview 생성에서 발생하지 않아야 한다.
- 문서 설명 요청도 candidate 수와 단계 수를 줄여야 한다.

### 9.3 UX 성공 기준

- 깨진 한글이 없어야 한다.
- 버전 질문이 없어야 한다.
- 불필요한 source card와 preview card가 없어야 한다.

## 10. 전환 원칙

`newv2.0.1`은 단순한 기능 개선이 아니라 제품 축 전환 버전이다.

전환 원칙:

- 문서 QA 챗봇에서 OCP 운영 챗봇으로 축을 바꾼다.
- 문서 RAG는 기본값에서 제거하고 보조 기능으로만 유지한다.
- OCP API 기반 read-first 멀티턴 assistant를 중심으로 구현한다.
- 현재 요구사항과 무관한 레거시 RAG 경로는 점진적으로 제거한다.
