# RAG Quality Hardening

작성일: 2026-03-31

## 목적

현재 RAG 시스템의 품질을 기본 동작 수준에서 실문서 기준으로 일관되게 신뢰 가능한 수준으로 끌어올린다.

이번 스펙의 핵심 목적은 다음 다섯 가지다.

- 문서에 실제로 존재하는 주제와 예시를 놓치지 않게 한다.
- 멀티턴 follow-up이 이전 문맥을 안정적으로 이어받게 한다.
- 코드/YAML 요청에서 불필요한 예시가 섞이지 않게 한다.
- 동일 질의 재호출 시 캐시가 기대대로 동작하게 한다.
- 차단 정책은 유지하되, 문서 관련 기술 질문이 과잉 차단되지 않게 한다.

## 요구사항

### 1. 문서 존재 토픽 미탐지 개선

다음과 같이 `extracted_markdown`에 실제 존재하는 주제는 단순 설명 질문에서도 문서 관련 질문으로 처리되어야 한다.

- ArgoCD
- Tekton
- RBAC
- Route
- StorageClass
- ConfigMap
- PVC / PV

문서에 실제로 존재하는 예시나 설명이 있을 경우, “관련 내용을 찾을 수 없음” 또는 “문서 관련 질문만 가능”으로 잘못 거절되면 안 된다.

### 2. 멀티턴 연속성 강화

다음 유형의 후속질문은 이전 턴의 문맥을 이어받아 처리되어야 한다.

- `그중 PVC만 더 자세히`
- `그 yaml에서 selector는 왜 써?`
- `그럼 Service yaml 예시 보여줘`
- `다시 RBAC 차이점만 설명해줘`
- `StorageClass 예시로도 바꿔줘`

특히 5턴 이상 연속 대화에서도 주제, 리소스, 답변 형태가 안정적으로 유지되어야 한다.

### 3. 코드/YAML 응답 정밀도 강화

사용자가 특정 리소스의 YAML 또는 코드 예시를 요청하면, 응답은 그 리소스와 직접 관련된 코드 위주로 구성되어야 한다.

예:

- `ConfigMap YAML 예시`
  - ConfigMap 중심이어야 함
  - 관련 없는 Pod 예시가 과도하게 섞이면 안 됨

- `Route 예시`
  - Route 예시가 문서에 있으면 실제 Route YAML이 우선되어야 함

### 4. 캐시 동작 일관성 확보

다음 동작이 보장되어야 한다.

- 같은 세션에서 같은 질문을 반복하면 캐시 히트가 관측되어야 한다.
- 같은 주제라도 설명 요청과 YAML 요청은 서로 다른 캐시로 취급되어야 한다.
- clarification/not-found 응답은 일반 grounded 응답과 구분되는 정책으로 다뤄져야 한다.

### 5. 차단 정책 유지와 과잉 차단 완화

다음은 계속 막아야 한다.

- 중국어 / 일본어 dominant 입력
- 문서 무관 질문
- 일반 상식, 레시피, 날씨, 주가, 맛집 추천

반대로 다음은 차단하면 안 된다.

- 문서에 존재하는 기술 주제 질문
- 한국어 + 기술 영문 혼합 질문
- 멀티턴으로 이어지는 문서 관련 referential follow-up

## 성공 기준

### 1. 테스트 결과 기준

수동 평가 결과 JSON 기준으로 다음을 만족해야 한다.

- `language_guard_cases.json`: 전부 통과
- `out_of_domain_cases.json`: 전부 통과
- `document_grounding_cases.json`: ArgoCD, Tekton, Route 관련 실패 제거
- `cache_behavior_cases.json`: 동일 질의 캐시 히트 검증 성공
- `multiturn_cases.json`: referential follow-up 실패 감소
- `long_multiturn_cases.json`: 5턴 이상 시나리오에서 문맥 단절 케이스 감소

### 2. 품질 기준

- 문서에 존재하는 주제를 “없음”으로 잘못 응답하는 비율이 낮아져야 한다.
- 특정 리소스 YAML 요청에서 무관한 코드 블록 혼입이 줄어야 한다.
- 후속질문에서 직전 리소스/형태를 이어받는 비율이 높아져야 한다.
- 동일 질의 반복 시 `observed_cached`가 실제로 잡혀야 한다.

### 3. 사용자 경험 기준

- 차단 응답은 일관된 정책 메시지로 보이되, 문서 관련 기술 질문까지 막아서는 안 된다.
- 결과 JSON은 사람이 빠르게 읽을 수 있어야 하며, 최종 답변과 캐시 여부가 바로 보여야 한다.

## 기술적 제약

- 오픈소스 RAG 프레임워크를 새로 도입하지 않는다.
- 현재 코드베이스의 직접 구현 구조를 유지한다.
- LLM은 기존 과제 제약을 유지한다.
- 세션 owner scope 분리는 유지한다.
- 멀티턴 메모리 구조와 procedure state는 유지하되 품질을 높인다.
- 현재 `tests/datasets` 및 `tests/results` 기반 수동 검증 흐름을 유지한다.
- 기존 차단 정책을 무력화하는 방향으로 바꾸지 않는다.

## 경계선

이번 스펙에 포함되는 것:

- retrieval / rerank / selection 품질 개선
- 멀티턴 follow-up 품질 개선
- 코드 추출 정밀도 개선
- 캐시 정책 실효성 보강
- 문서 관련 기술 질문의 과잉 차단 완화

이번 스펙에 포함되지 않는 것:

- 새로운 제품 기능 추가
- UI 전면 개편
- 인증 체계 재설계
- 평가 데이터셋 자체의 의미 변경
- 일반 지식 답변 허용 범위 확대
- 문서에 없는 내용을 LLM 상식으로 보완하는 정책
