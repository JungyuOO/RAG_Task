# RAG Task newv1.0.1 Spec

작성일: 2026-04-10  
상태: Draft

## 1. 목적

`newv1.0.1`의 목적은 현재 RAG 챗봇을 단순 문서 질의응답 데모 수준에서 재구성하여, 실제 제품/서비스 수준의 OpenShift 운영 Assistant로 전환하는 것이다.

이번 버전은 기존 기능을 부분 보정하는 수준이 아니라, 다음 요구를 반영한 구조 재설계를 목표로 한다.

- 챗봇 기능은 유지한다.
- 그러나 기존 PDF 중심, 불안정한 멀티턴, 느린 응답, 약한 렌더링, 약한 근거 표현, 버전 혼재 문제를 해소한다.
- 단순히 문서를 읽어주는 챗봇이 아니라, 향후 타 기업에 제공 가능한 서비스형 제품 구조를 설계한다.

## 2. 재설계 범위

이번 재설계는 아래 범위를 포함한다.

1. 문서 전처리 및 인덱싱 구조 재설계
2. 멀티턴 질의응답 구조 재설계
3. 답변 생성 및 답변 포맷 구조 재설계
4. 근거 표시 및 문서 탐색 UX 재설계
5. 응답 지연과 상태 표시 구조 재설계
6. UI/디자인 재설계
7. OCP API 연계 구조 설계
8. 단일 버전 운영 전략 수립
9. 삭제 대상 코드 / 유지 대상 코드 기준 정리
10. UTF-8 인코딩 정책 고정

## 3. 현재 문제 요약

### 3.1 답변 품질 문제

- LLM 최대 토큰 제한으로 인해 답변이 문장 중간에서 어색하게 끊긴다.
- 답변이 질문에 직접 답하기보다, 목차/서문/메타 문장을 재조합하는 경우가 있다.
- 멀티턴 후반부로 갈수록 이전 답변이나 이전 문서로부터 질문 의도를 잘못 이어받는 경우가 있다.
- 사용자가 짧고 모호하게 묻는 경우, 질문 의도를 충분히 해석하지 못하고 엉뚱한 답변이 생성된다.
- 요약, 체크리스트, 단계화, 비교 요청이 실제로는 직전 답변 재가공이어야 하는데 새 검색으로 처리되며 품질이 흔들린다.

### 3.2 속도 문제

- 첫 답변까지 시간이 길어 사용자는 시스템이 멈춘 것처럼 느낀다.
- retrieval, reranking, answer generation, rendering 병목이 분리되어 보이지 않는다.
- 스트리밍은 있으나 실제 백엔드 상태를 웹에서 명확히 이해하기 어렵다.

### 3.3 문서 구조 문제

- PDF 기반 추출물은 구조 정보가 약하고, 페이지 기반 조각이 많아 실제 서비스용 근거 표현이 부자연스럽다.
- 공백, 표, 섹션, 코드 블록이 완전히 정규화되지 않은 채 인덱싱 후보로 사용된다.
- 표 구조가 본문 문자열 안에 섞여 들어가 retrieval 품질을 해친다.
- 법무/저작권/목차/초반 서문 같은 low-signal 영역이 답변 후보에 끼어든다.

### 3.4 프론트엔드 문제

- 마크다운/코드/리스트/표가 보기 좋게 렌더링되지 않는다.
- ```, `-`, 표 구조 등이 단순 텍스트처럼 보인다.
- 자료 근거가 PDF 페이지 수준으로만 연결되어 실제로 “어디서 가져왔는지”를 신뢰하기 어렵다.
- 청크 보기 버튼이 느리고, 사용자는 현재 어떤 단계에서 기다리는지 알 수 없다.
- 전체 화면 인상이 딱딱하고, 도입 가능한 제품/SaaS/운영 콘솔 수준의 디자인 완성도가 부족하다.

### 3.5 아키텍처 문제

- 검색이 필요한 턴과 단순 재가공/요약 턴이 명확히 분리되지 않는다.
- 세션 메모리, 토픽 유지, 문서 anchor 유지가 일관되지 않다.
- 버전 선택 기능이 시스템 전체를 복잡하게 만든다.
- 문서 검색 결과와 답변 형태 간의 정합성을 검증하는 계층이 약하다.

### 3.6 서비스 확장성 문제

- 현재 구조는 문서 질의응답만 가능하고, 실제 운영 행동과 이어지지 않는다.
- 향후 사업화를 위해서는 “설명만 하는 챗봇”이 아니라 “실제 OCP 상태를 조회하고, 필요한 경우 운영 작업으로 연결되는 서비스”가 필요하다.

## 4. 제품 방향

`newv1.0.1`은 다음 포지션의 제품을 목표로 한다.

### 4.1 기본 포지션

- OpenShift 4.20 전용 운영/가이드 AI Assistant
- 문서 기반 답변 + 운영 컨텍스트 유지 + 근거 탐색 UX 제공

### 4.2 확장 포지션

- 운영자용 문서 기반 Assistant
- 고객사 운영 가이드 + 공식 문서 + 실제 OCP API 상태를 결합한 Hybrid 운영 도우미
- 향후 액션 제안, 점검 체크리스트, 리소스 상태 확인, 운영 자동화 진입점 제공

추가 제품 요구:

- 이 Assistant는 내부 운영자만이 아니라 사업 담당자와 고객사 사용자도 직접 사용할 수 있어야 한다.
- 따라서 답변은 단순 설명문으로 끝나면 안 된다.
- 사용자가 무언가를 물으면:
  - 먼저 이해 가능한 설명
  - 그 다음 바로 쓸 수 있는 예시
  - 필요 시 YAML / CLI / 체크리스트 / 관련 리소스
  가 함께 제시되어야 한다.

## 5. 버전 전략

### 5.1 단일 버전 전략

이번 버전부터 문서 버전 선택 기능은 제거한다.

- 지원 제품 버전은 `OpenShift 4.20` 단일 버전으로 고정
- 공식 문서도 4.20만 유지
- 고객사 문서도 4.20 기준으로 정리

### 5.2 이유

- 버전 선택은 retrieval 범위를 불필요하게 넓히고, UX도 복잡하게 만든다.
- 현재 목표는 “여러 버전 대응”이 아니라 “현재 운영 버전에 대해 정확한 답변”이다.
- 4.20 단일 버전 운영이 멀티턴 품질과 서비스 구조 안정화에 유리하다.

## 6. 목표 아키텍처

### 6.1 전체 파이프라인

목표 파이프라인은 다음과 같다.

1. 입력 수신
2. 질문 분류
3. 세션/토픽 상태 해석
4. 검색 필요 여부 판단
5. 문서 retrieval 또는 직전 답변 transformation
6. 최종 답변 생성
7. 근거 렌더링 payload 생성
8. 스트리밍 응답
9. 세션 메모리/토픽 상태 갱신

### 6.2 질문 처리 분기

질문은 최소 세 가지로 분기한다.

1. `retrieval turn`
   새 정보를 문서에서 찾아야 하는 질문

2. `follow-up retrieval turn`
   같은 문서/같은 토픽 안에서 더 자세히 묻는 질문

3. `transformation turn`
   직전 답변을 요약, 체크리스트, 단계, 비교 형태로 바꾸는 질문

핵심은 모든 후속 질문을 무조건 retrieval로 보내지 않는 것이다.

## 7. 백엔드 설계 요구사항

### 7.1 Streaming 응답

필수 요구사항:

- 토큰 단위 또는 chunk 단위 스트리밍 유지
- 스트리밍 중간 상태를 프론트에서 시각적으로 표현 가능해야 함
- `status -> partial answer -> final answer -> context payload` 흐름 정리

### 7.2 실제 상태 기반 응답 진행 표시

답변 생성 과정은 최소 다음 상태를 백엔드에서 구분하고, 프론트는 이를 그대로 표시해야 한다.

- query_interpretation
- source_filtering
- retrieval
- reranking
- answer_generation
- citation_rendering

목표:

- 느리더라도 “멈춘 것처럼 보이지 않는” UX
- 사용자가 현재 무엇을 기다리는지 알 수 있는 UX

### 7.3 답변 지연 개선

답변이 너무 느린 문제는 이번 버전에서 반드시 개선해야 한다.

개선 목표:

- 첫 토큰이 빠르게 보여야 한다.
- retrieval, reranking, answer generation 시간이 분리 측정되어야 한다.
- 불필요한 reranking, broad retrieval, 재검색을 줄여야 한다.

구조 원칙:

- 새 retrieval가 필요한 질문과 직전 답변 재가공 질문을 분리
- reranker는 항상 수행하지 않고 조건부 수행
- answer route별 토큰 budget을 분리
- 응답 길이 제한에 걸리면 “중간에 잘리는 답”이 아니라 “완결된 짧은 답”이 나오게 한다

### 7.4 답변 구성 정책

최종 답변은 단순 서술형 한 덩어리로 끝내지 않는다.

기본 구성:

1. 직접 답변
2. 짧은 근거 요약
3. 필요 시 확장 가능한 실행/예시 블록

예시:

- Pod 개념을 물으면
  - 먼저 Pod 설명
  - 그 아래 토글형 `Pod 생성 예시 YAML`
  - 그 아래 토글형 `관련 oc 명령`

- Route 53 준비를 물으면
  - 먼저 설명
  - 그 아래 체크리스트
  - 그 아래 관련 문서 source card

즉 Assistant는 “답변”과 “실행 가능한 보조 정보”를 함께 내보내야 한다.

### 7.5 대화 상태 관리

세션 메모리는 단순 LLM 히스토리 전달이 아니라 직접 구조화해서 유지한다.

유지해야 할 상태:

- active topic
- selected sources
- latest grounded sources
- latest grounded sections
- answer route
- recent citations
- last user focus

원칙:

- 최신 assistant 답변의 실제 근거를 다음 턴 anchor로 사용
- 오래된 source 누적보다 최신 answer citation을 우선
- follow-up일수록 범위는 좁아져야 한다

### 7.6 Retrieval 구조

기본 retrieval 구조는 유지하되, 다음 원칙을 따른다.

- 전체 corpus를 넓게 검색하되 1차 후보는 제한된 개수만 사용
- low-signal chunk는 후보에서 제거
- 필요할 때만 reranker 사용
- follow-up은 같은 문서/같은 섹션 continuity를 강하게 유지

low-signal 제거 대상:

- TOC
- legal notice
- copyright
- abstract
- section index page
- 문서 서문/법무성 front matter

### 7.7 Vector Index 구조

Vector index 구조는 직접 설계하되, 저장 및 유사도 검색 엔진으로 `pgvector`를 공식 채택한다.

원칙:

- PostgreSQL + pgvector 사용 허용
- 그러나 pipeline 설계는 직접 수행
- 즉 다음은 직접 구현/설계 대상이다.
  - chunk schema
  - metadata schema
  - candidate generation
  - low-signal filtering
  - follow-up anchoring
  - rerank 조건
  - answer route 분기

### 7.8 Response-shape validation

답변은 질문 형태와 맞아야 한다.

예:

- checklist 요청이면 checklist 구조여야 함
- 단계 요청이면 단계형 구조여야 함
- 비교 요청이면 최소 두 축 이상 비교가 나와야 함
- 코드/YAML 요청이면 실제 코드 블록 또는 구조화된 항목이 있어야 함

형태가 맞지 않으면:

- 다른 candidate를 다시 선택하거나
- 변환용 fallback을 사용하거나
- 명시적으로 부족함을 말해야 한다

## 8. 문서 처리 구조 재설계

### 8.1 PDF 중심 구조 축소

PDF는 원본 자산으로 유지하되, 서비스 질의응답의 주요 본문은 HTML/구조화 문서 형태로 전환한다.

목표:

- PDF는 다운로드/원문 보기용
- 질의응답용 본문은 HTML + structured metadata 기반

### 8.2 문서 파이프라인

새 파이프라인:

1. 원본 PDF/MD 수집
2. 구조 추출
3. HTML 문서화
4. 텍스트/표/코드/섹션 metadata 분리 저장
5. retrieval용 텍스트 인덱싱
6. 렌더링용 HTML payload 저장

### 8.3 Chunk 설계

청크는 단순 문자열 덩어리가 아니라 구조 단위여야 한다.

청크 저장 항목 예시:

- plain_text
- normalized_text
- section_title
- section_path
- parent_headings
- block_type
- code_language
- table_schema
- html_fragment_id
- page anchors
- doc group

### 8.4 표와 코드 처리

표와 코드는 본문 문자열에 섞어 넣지 않는다.

- 표는 구조화된 metadata로 분리
- 코드는 fenced block 또는 structured snippet으로 분리
- retrieval 시 text index와 metadata index를 함께 사용

추가 요구:

- 실행 예시용 YAML / CLI / 리소스 스니펫은 answer 본문과 분리된 구조로 저장 가능해야 한다.
- 즉 retrieval 결과에서
  - 설명용 텍스트
  - 예시 YAML
  - 예시 CLI
  - 표/체크리스트
  를 따로 선택할 수 있어야 한다.

### 8.5 공백/정규화

필수 정규화:

- 불필요한 개행 제거
- 토큰화 방해 공백 정리
- OCR/추출 노이즈 제거
- 페이지 헤더/푸터/법무 문구 제거

## 9. 청크 보기 UX / API 재설계

### 9.1 목표

청크 보기 또한 백엔드 상태 기반 UX로 전환한다.

필수:

- `chunk status` API 제공
- `chunk list` API 제공
- 프론트는 상태를 먼저 받고, 결과는 준비되는 즉시 표시
- 대형 문서라도 “읽는 중 / 정리 중 / 준비 중” 상태를 사용자에게 보여줄 수 있어야 한다

### 9.2 청크 API 목표

- 청크 목록은 페이지네이션 기본
- chunk metadata와 text preview 분리
- 전체 전문은 chunk detail API에서만 조회
- 자료실 목록 호출과 청크 보기 호출이 서로 병목을 만들지 않게 분리

## 10. 프론트엔드 UX 요구사항

### 10.0 디자인 방향

이번 버전은 기능 재설계와 함께 UI/디자인도 전면 재설계한다.

디자인 목표:

- 스타트업 SaaS처럼 정돈된 인상
- 공기업/대기업 납품형 서비스처럼 신뢰감 있는 운영 콘솔 분위기
- 과도한 장식보다 정보 구조와 상태 전달 우선

핵심 방향:

- 차분하고 신뢰감 있는 톤
- 스캔 가능한 정보 밀도
- 채팅, 근거, 상태, 문서 탐색을 분리한 레이아웃
- “챗봇 화면”이 아니라 “문서+운영 Assistant 서비스”처럼 보이는 디자인

권장 레이아웃 방향:

- 상단: 현재 버전 / 현재 토픽 / 상태 / 연결 정보
- 중앙: 대화 영역
- 우측 또는 하단 패널: 근거 / source card / preview / OCP 상태
- 자료실과 청크 보기: 별도 작업 패널 또는 drawer

디자인 원칙:

- 과하게 둥글고 장난스러운 컴포넌트 금지
- 지나치게 밋밋한 내부툴 느낌도 지양
- 운영도구 같은 명확함과 제품 같은 polish를 동시에 확보

필수 요구:

- typography 정리
- spacing system 정리
- 상태 badge / source card / preview panel 재설계
- 코드/YAML/표 렌더링 가독성 강화
- 문서 탐색 UI를 채팅과 분리

성공 기준:

- 외부 고객 데모에 바로 써도 되는 수준
- “테스트 페이지”가 아니라 “도입 가능한 서비스”처럼 보여야 함

### 10.1 답변 렌더링

답변은 plain text가 아니라 markdown renderer 기반으로 그려야 한다.

필수:

- paragraph
- bullet
- numbered list
- table
- code block
- inline emphasis

목표:

- ``` 는 코드 블록으로
- `-` 는 bullet로
- 표는 표로
- citation은 버튼/태그형으로 보이게

추가 요구:

- 답변 하단에 토글형 확장 블록을 둘 수 있어야 한다.
- 예:
  - `예시 YAML 보기`
  - `관련 oc 명령 보기`
  - `운영 체크리스트 보기`
  - `참고 문서 더 보기`

- 본문은 설명 중심
- 하단 확장 블록은 실행/예시/체크리스트 중심

이 구조를 기본 answer UX 패턴으로 채택한다.

### 10.2 근거 표현

현재 `>` 위주의 단순 표시는 폐기한다.

대신:

- 클릭 가능한 source card
- HTML 기반 섹션 highlight
- 문서 내 실제 heading 이동
- PDF fallback link
- 동일 답변 안에 여러 source가 있으면 각각 분리된 근거 블록으로 표시
- 단순 `>` 반복이 아니라 source마다 문서명 / 섹션 / 페이지 / 발췌 위치가 보이게 한다
- “같은 문서, 같은 페이지”만 반복 표시되는 구조를 줄이고 실제 사용된 source 단위를 더 세밀하게 보여줘야 한다

즉 “이 답이 어디에서 왔는지”를 사람이 신뢰할 수 있는 방식으로 보여준다.

### 10.3 대화 상태 표현

웹에서 최소한 다음을 확인할 수 있어야 한다.

- 현재 질문 유형
- 현재 참조 문서
- 현재 토픽
- 현재 answer route
- 스트리밍 진행 상태
- 현재 시스템 상태를 보는 패널이 시각적으로 분리되어야 함

## 11. OCP API 확장

### 11.1 목표

문서 챗봇을 운영 Assistant 서비스로 확장한다.

### 11.2 1단계 OCP API 범위

초기에는 안전한 read-only 중심으로 시작한다.

- 클러스터 정보 조회
- 프로젝트/네임스페이스 상태 조회
- Pod / Deployment / Service / Route 상태 조회
- 이벤트 조회
- 실제 리소스 YAML 조회

추가 목표:

- 문서 기반 설명 뒤에 실제 OCP 상태를 함께 보여줄 수 있어야 한다.
- 예:
  - “Pod이란 무엇인가?”를 물으면 설명 + 예시 YAML + 실제 클러스터 Pod 상태 조회 진입점
  - “현재 deployment 상태 보여줘”를 물으면 설명보다 실제 상태 패널을 우선 보여줄 수 있어야 한다

즉 사용자는 “문서 설명”만 받는 것이 아니라,

- 현재 Pod 상태
- 현재 Deployment 상태
- 현재 리소스 정의 YAML

을 Assistant 안에서 함께 확인할 수 있어야 한다.

### 11.3 이후 확장

향후에는 승인 기반 반자동 액션으로 확장 가능하다.

- 점검 체크리스트 자동 생성
- 권장 조치안 생성
- 승인 기반 실행

핵심 원칙:

- 바로 위험한 write action은 하지 않는다
- 설명 + 제안 + 승인 기반 실행 구조로 간다

## 12. 서비스 차별성

이 제품의 차별성은 “문서를 읽어주는 챗봇”이 아니라 아래 조합에 있다.

- 공식 문서 + 고객사 운영 가이드 + 실제 OCP 상태 조회
- 멀티턴 문맥 유지
- 근거를 사람이 읽을 수 있는 방식으로 표시
- 문서 검색과 운영 행동을 연결하는 구조

## 13. 삭제/정리 원칙

이번 재설계에서는 필요 없는 코드는 빠르게 제거한다.

원칙:

- 쓰이지 않는 경로는 즉시 삭제
- 중복 answer route 제거
- 중복 렌더링 경로 제거
- legacy version handling 제거
- 4.20 외 버전 관련 복잡성 제거

## 14. 인코딩 정책

전체 텍스트 자산과 코드 파일은 UTF-8 고정 원칙을 따른다.

필수:

- markdown
- html
- json
- python
- js
- spec 문서

목표:

- PowerShell 출력 인코딩과 별개로, 저장 파일은 항상 UTF-8
- 깨진 한글 문자열을 남기지 않는다

## 16. 수용 기준

### 16.1 품질

- 짧은 질문에도 후속 문맥이 유지되어야 함
- checklist / 단계 / 비교 요청이 실제 형태에 맞게 답해야 함
- front matter, 메타 편집 문구, 목차 조각이 답변에 나오지 않아야 함
- 설명형 답변 뒤에 필요한 경우 예시 YAML / CLI / 체크리스트가 확장 블록으로 제공되어야 함

### 16.2 속도

- 체감상 멈추지 않는 스트리밍
- retrieval / transform turn을 구분하여 불필요한 긴 지연 제거
- 답변 상태가 웹에서 실제 단계 기반으로 보여야 함
- chunk 보기 버튼도 장시간 무반응이 아니라 상태를 표시해야 함

### 16.3 제품성

- 단순 답변이 아니라 근거 탐색 경험이 있어야 함
- 향후 OCP API 기반 기능 확장이 가능해야 함
- 실제 리소스 상태와 YAML을 함께 볼 수 있어야 함
- 사업 담당자나 고객사 사용자가 봐도 “바로 쓸 수 있는” 답변 구조여야 함

## 17. 이번 문서의 의미

이 문서는 현재 구현을 미세 조정하는 문서가 아니다.

이 문서는 기존 버전 구조를 사실상 종료하고, 챗봇 기능은 유지하되:

- 문서 처리 구조
- 멀티턴 구조
- 렌더링 구조
- 상태 표시 구조
- OCP API 기반 서비스 확장 구조

를 다시 설계하는 `newv1.0.1`의 기준 문서다.

## 18. 추가 제품 UX 요구

이번 버전은 기능/구조 재설계뿐 아니라, 실제 기업형 제품 수준의 UX를 목표로 한다.

추가 요구:

- 설명형 답변 + 실행 가능한 예시를 한 화면 안에서 자연스럽게 보여줄 것
- 답변 하단에 토글형 보조 블록 제공
  - 예시 YAML
  - 관련 `oc` 명령
  - 운영 체크리스트
  - 실제 OCP 상태
  - 관련 리소스 YAML
- 다중 source를 source card 단위로 분리해서 보여줄 것
- “같은 페이지를 반복해서 인용하는 느낌”이 아니라, 실제 사용된 근거를 구조화해서 보여줄 것

## 19. 골든 데이터셋 전략

### 19.1 목적

이번 버전부터는 시나리오 테스트만으로 품질을 판단하지 않는다.
별도의 `golden dataset`을 두고, 실제 답변 품질과 구조 품질을 반복 검증할 수 있어야 한다.

### 19.2 golden dataset 정의

golden dataset은 다음 항목을 포함하는 기준 데이터다.

- 질문
- 질문 유형
- 기대 문서군
- 기대 source family
- 기대 핵심 키워드
- 기대 answer shape
- 허용 가능한 변형 범위
- 금지 패턴

예:

- checklist 질문인데 checklist 구조가 아니면 실패
- 비교 질문인데 한 축이 없으면 실패
- front matter / TOC / 법무 문구가 나오면 실패

### 19.3 용도

- 회귀 테스트
- 품질 검증
- prompt / retrieval / rendering 개선 전후 비교
- 배포 전 승인 기준

## 20. 데이터 파이프라인 자동화

### 20.1 목적

문서 수집, 구조화, 인덱싱, 검증을 수작업이 아니라 자동화 파이프라인으로 관리한다.

### 20.2 자동화 범위

자동화 대상:

1. 공식 문서 수집
2. 고객사 문서 수집
3. 문서 구조 추출
4. HTML 전환
5. 표/코드/섹션 metadata 추출
6. chunk 생성
7. embedding 생성
8. pgvector 적재
9. golden dataset 기반 품질 검증
10. 결과 리포트 생성

### 20.3 파이프라인 원칙

- 수동 ad-hoc 스크립트 의존을 줄인다
- 단계별 산출물이 남아야 한다
- 실패 시 어느 단계에서 실패했는지 추적 가능해야 한다
- 재실행 가능해야 한다
- 부분 재실행과 이어받기가 가능해야 한다

### 20.4 필수 산출물

- 정규화된 문서 산출물
- HTML 산출물
- 구조화 metadata 산출물
- 인덱싱 결과
- 품질 검증 결과
- 성능 측정 결과

### 20.5 운영 목표

- 새 문서 투입 시 자동 파이프라인으로 반영 가능
- 품질 저하가 생기면 golden dataset이 바로 감지
- 제품 배포 전에 자동 리포트로 품질을 확인 가능
